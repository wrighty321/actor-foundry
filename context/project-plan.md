## Risks & unknowns
| Risk | Known / Unknown | Mitigation, or cheapest test to resolve it |
|---|---|---|
| Chosen site sits behind anti-bot (Cloudflare, DataDome) and needs residential proxies, so the actor runs at a loss | Unknown | Plain `fetch` of three target pages before committing to a site; price from measured compute units on the fixture run |
| In-app scheduled tasks fire only while the app is open, so the maintainer cannot live there | Known | Ruled 2026-10-18: GitHub Actions cron; milestone 1 proves 7 unattended days before any actor depends on it |
| Public professional data is still personal data under UK GDPR; a complaint or takedown lands on the user's KYC'd account | Known | Lawful basis recorded in each ruling request; private and sensitive data excluded; honour takedown requests by pausing the actor |
| The Apify token, Telegram bot token and the runner's Claude credential (`CLAUDE_CODE_OAUTH_TOKEN`) live as GitHub repository secrets; a workflow change could exfiltrate them | Known | Each secret scoped to one workflow; the Claude credential only in the manually triggered repair workflow, never in the daily check or the wiki pull; PRs that touch `.github/` get the same adversarial review as actor code; no third-party actions without a pinned SHA |
| The Store `notice` field cannot be set through the Update Actor API, so "paused with a status message" has no Console-free route via `notice` | Known (Python and JS client references read 2026-10-18; the REST page itself failed to fetch twice) | Pause is a kill-switch record the actor reads at start plus a flagged `description`, both via API and read back. Whether a paused run exits as failed (honest; counts against the 30-day stats) or succeeds with zero rows (clean stats; looks like a crash by the brief's standard) is an architecture decision for `/architect` |
| Apify account has no KYC, so no payout and no agentic-payment eligibility until it is done | Known | KYC is a human step; the plan assumes it happens before milestone 2's publish, which the user has not yet confirmed |
| Pay-per-event pricing below platform cost (negative profit) | Known | Weekly read of profit per actor in Apify Actor analytics; `apify-actor-start` synthetic event on; memory limits set |
| Nobody finds the actors on the Store | Unknown | Read paid and free user counts 30 days after each publish; promote per Apify's marketing checklist only if zero |
| Grok Bot shares one computer and its credentials across every bot on the account | Known | The watcher is read-only; the Apify token lives in this repo's `.env` and is never placed on the Grok Bot computer |
| A target site's terms forbid scraping, or the data turns out personal | Known | The candidate note quotes the terms line and flags it; human ruling before build, recorded in `decisions.md`; private and sensitive data excluded before scoring |
| A Claude cloud routine cannot reach the repo or run the synthesis or the target research on the plan | Unknown | Milestone 1b's first synthesis run; if it fails, `/wiki-refresh` run by hand is the fallback (skill not yet written) and the target research runs as a manual session until a runner is found |
| The wiki and the target agent cost more attention than they save (Kun: durable loops pay off only with recurring inputs) | Known | Overridden at interview and again on 2026-10-18; judged by whether an approved candidate from the target agent becomes actor #1 and whether 1b and 1c's hours come out of milestones 1–3 |
| Three tracks (1, 1b, 1c) at 6–8 hrs/week push milestone 1 past its slip date of 2026-11-15 | Known | Order: the hand-run stub week first, then 1 and 1b's weekly pull together (same GitHub Actions setup), then 1c on demand; 1d waits for two snapshots and the repair workflow for the first real escalation (ADR 013); the slip rule in `vision.md` still applies to 1 |
| GitHub `schedule` runs can be delayed or dropped, most at the top of the hour | Known (GitHub docs, read 2026-10-18) | Crons run off the hour; `maintainer/STATUS.md` and a non-zero exit make a missed day visible; the in-actor preflight (ADR 009) means a late check no longer leaves wrong rows selling |
| The Store list envelope's `count` overstates the items returned, so a pull reconciled on the envelope writes a short snapshot | Known (observed 2026-10-18: `count: 1000`, 948 items; `count: 100`, 93; identical on repeat) | Reconcile on unique ids received against totals seen and the previous snapshot; write nothing on failure; a committed test page with `count` > items |
| The Obsidian Git plugin opened on `wiki/` finds no `.git` (it sits one level up) | Known | Set the plugin's custom base path to the repo root, or `git pull` by hand; verified at 1b |
| An agent commit under `actors/**` reaching `main` would deploy to the Store | Known | `main` requires PRs with the Actions app bypassed for log commits; the deploy job runs only when the push actor is the user; agent commits carry trailers (ADR 011) |
| Patterns drawn from the top 300 teach survivorship: top actors are often top because they were first, and weak ones are absent from a users ranking | Known | Rank by 30-day users; a deliberate weak-actor sample in each pull; claims compared within category and graded observed / documented / confirmed (`wiki/README.md`) |
| Third-party text read by the research agents (READMEs, reviews, forum posts) reaches the builder's instructions | Known | `wiki/playbook/` changes only by a PR the user approves; synthesis pages are evidence, never instruction |
| Obsidian shows a stale wiki because the runners commit on GitHub | Known | Obsidian Git plugin set to pull on open, or `git pull` before each candidate review |
| Retention and feedback data for competitors is not in the Store API | Known | Inferred from user trends across snapshots and graded as such; real numbers only from our own actors' analytics in `wiki/first-party/` |
| The builder cannot handle a site unaided and the user finishes it by hand | Known | Expected for roughly half of early candidates; each fix lands in the actor template so the next build absorbs it |
