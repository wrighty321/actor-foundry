## 1. Apify platform facts

Source: Apify docs, read 2026-10-18 through the Apify MCP docs tools —
`https://docs.apify.com/actors/publishing/monetize` (fetched in full),
`/actors/publishing/monetize/pay-per-event`, `/monthly-payouts`, `/pricing-and-costs`,
`/actors/running/usage-and-resources`, `/actors/running/standby`,
`/actors/development/permissions/migration-guide`, `/sdk/python/docs/concepts/actor-events`,
`/sdk/python/docs/concepts/error-handling` (the last eight via search excerpts, not full pages).
Items marked *(knowledge)* were not re-checked against a page that day.

**Money**
- Two pricing models can be published: **pay per event (PPE)** — the actor charges for events
  it defines in code — and **pay per usage**, where the user pays only platform costs and the
  developer earns nothing. A "rental" model is still linked from the docs but is not in the
  publishable list; read as legacy (inference — the rental page failed to load).
- Apify keeps **20%** of actor revenue. Apify never charges the developer when the actor earns
  nothing.
- For PPE actors Apify **deducts platform usage costs** (compute, proxies, storage, data
  transfer) from the payout. If the event prices don't cover them, the actor has negative
  profit, but the developer never pays Apify for other users' runs. An actor with negative
  profit counts as $0 for aggregation, so it can't eat another actor's profit (docs example:
  −$90 + $100 pays $100, not $10).
- Avoiding negative profit, per the docs: set memory limits, respect user spending limits,
  enable the `apify-actor-start` synthetic event. Platform costs *can* be passed to users
  ("Pay per event + usage") while calibrating prices, but it lowers the quality score and
  excludes the actor from per-request agentic payments — temporary use only.
- Testing your own actor is charged to your own prepaid usage. The **Creator plan** gives
  $500 of prepaid usage for the first 6 months.
- **Payouts** are monthly; minimum **$20 for PayPal and Wise, $100 for other methods**; below
  that the balance rolls over. **Identity verification (KYC)** must be complete or nothing is
  paid and no actor is eligible for agentic payments.
- Agentic payments: agents buying a prepaid token via **x402** or **MPP** can run any actor with
  limited permissions, whatever its pricing model. Agents paying per request (e.g. **Skyfire**)
  can run only actors that are PPE, charge for events only (no "+ usage"), run with limited
  permissions, and do not use Standby mode. Apify checks this automatically.
- Free users: limits are allowed but must be stated in the README and input schema, and a hit
  limit must exit gracefully with a status message, never look like a crash.
- Actor analytics (Console → Development → Insights → Analytics): revenue, costs and profit over
  time, paid and free user counts, cost per 1k results, run success rate, funnel; exportable
  as JSON. This is where the weekly profit-per-actor check in the plan reads from.

**Mechanics**
- Three stages: **source** (code, `Dockerfile`, `.actor/actor.json`, input schema) → **build**
  (a Docker image with a version like `0.1` and a tag like `latest`) → **run** (one execution
  of a build with an input JSON, memory size and timeout). Deploy with `apify push`, or link a
  Git repo so every push rebuilds.
- Runs start from the Console, the REST API, schedules, saved tasks, Make/n8n/Zapier, or an AI
  agent through Apify's MCP server.
- Each run gets three storages: **dataset** (append-only result rows), **key-value store**
  (named files; the input is `INPUT`), **request queue** (URLs still to crawl, deduplicated).
  Named storages persist across runs *(knowledge)*.
- **Compute units**: 1 CU = 1024 MB of memory for 1 hour, billed per second. More memory also
  buys a proportionally larger CPU share. Platform usage = CUs + data transfer + proxy usage
  (residential and SERP are the expensive ones) + storage operations.
- The SDK emits `PERSIST_STATE` every 60 s by default and again, with `is_migrating=True`, on
  `MIGRATING`; save progress to the key-value store on it or a migrated run starts over (and
  on PPE can charge the same result twice).
- PPE charging in Python: `Actor.push_data(item, charged_event_name="...")` writes the row and
  bills in one call. When the user's spending limit (`ACTOR_MAX_TOTAL_CHARGE_USD`) is reached the
  SDK caps charging and writing *without raising*; check `event_charge_limit_reached` on the
  returned `ChargeResult` and finish cleanly.
- **Standby mode** keeps the actor running as an HTTP server (Apify scales copies by traffic
  and idles them out); `actor.json` can declare an MCP endpoint path so the actor becomes an
  MCP server at a stable URL. PPE recommended there. Not eligible for per-request agentic
  payments (see above).
- **Limited permissions**: the actor touches only its own default storages plus what the user
  passes in; an actor that reads its input and writes to its default storages needs no change.
  Recommended minimum SDKs for it: JS `apify@3.4.4`, Python SDK v3.0.0. Full permissions
  exclude the actor from per-request agentic payments.
- Local loop *(knowledge)*: `apify create` → `apify run` (storages land in `./storage`) →
  `apify push`.

**Economics example used in planning** (illustrative, not measured): $2 per 1k results,
500k results/month → $1,000 revenue, −20% = $800, minus perhaps $150 compute and proxies
≈ $650. The proxy line is where the real variance is.

## 2. Store gap-check heuristics (for milestone 2 target selection)

Source: the 2026-10-18 session's own reasoning plus Kun Chen's public opinion map
(`kunchenguid/kun` at commit `6182bc1`): "most of the boring stuff already exists as a library
or service" (2026-08-09) and "good ideas start with named people who care about a real
problem". Not validated by any shipped actor yet.

Interview ruling, 2026-10-18: the user has no target sites in mind and does not want to pick by
hand; selection starts from an assessment of the current top Store competitors (what they
offer, for whom, at what price, how well maintained) and fills gaps from there. The heuristics
below are the lens that assessment uses, and the actor intelligence bank (see the plan) is
where it is kept current.

Look for demand that is already proven and badly served, in this order:
1. Apify Store searches that return nothing good for a query people plausibly type.
2. Existing actors with low ratings or reviews saying "broken", "stale", "no longer works".
3. Niche B2B data people already pay for or copy by hand: trade directories, public tenders,
   planning applications, industry registries, licensing bodies.
4. GitHub repositories that scrape site X, with stars and open issues (a proxy for demand and
   for how often the site changes).
5. r/webscraping, Upwork and Stack Overflow posts asking how to scrape X.
6. Any Firecrawl or Apify job the user has run more than twice by hand.

Before committing to a site: a plain `fetch` of three target pages from a non-residential IP.
A Cloudflare or DataDome challenge means residential proxies, which means the economics in §1
get much worse; the site is dropped or priced accordingly. Also read the site's terms and
classify the data (personal data and login walls are hard exclusions in the brief).

The differentiator to sell on is reliability — "the version of X that doesn't break" — which
is what the fixture and maintainer loop exist to make true.

## 3. Watcher feed candidates (for milestone 5, deferred)

Source: the 2026-10-18 session, from knowledge; none of these feeds was fetched or tested
that day. Ordered by how early a site shows up in them.
- **Launch feeds** (earliest): Product Hunt launches, Hacker News "Show HN" and front page,
  GitHub stars for developer-facing sites, X mentions (Grok Bot's native X search is the
  reason the watcher was placed there).
- **Rank lists** (later; a new site only appears once it is already mid-sized): Tranco
  (free daily top-1M list with history, so rank deltas are computable), Cloudflare Radar top
  domains, app-store rankings.
- **Paid**: Similarweb, better data, excluded while spend is "existing plans only".

Design rule from the vision: the watcher is mostly deterministic — a script computes deltas
and a model reads the shortlist once a day — and it holds no credentials for this repo.
Growth adjusts a candidate's score and ship date; it does not select the candidate.

## 4. Grok Bot facts

Source: `https://docs.x.ai/grok-bot/overview` (page dated 2026-10-07, read in full
2026-10-18) and, for pricing and allowance detail, a secondary write-up
(`coursiv.io/blog/grok-bot`, 2026-09-11). Also saved as memory `grok-bot-capabilities.md`
in `random`; this copy is the one this repo relies on.
- Named persistent bots on a cloud computer with a browser, filesystem and terminal.
  Routines run on a schedule or trigger; "teach a task" records a browser workflow as a skill.
  Bots message each other, share group chats and hand off tasks. X integration (search posts,
  timelines, mentions) added 2026-08-29.
- **All bots on an account share one computer**: files, browser sessions and CLI credentials
  are shared, and deleting a bot does not revoke them. This is why the builder and maintainer
  are not there and why the Apify token must never be placed on it.
- Per-bot charters, memory and approval rules exist; isolation between bots does not.
- Access comes with paid Cursor plans ($20 / $60 / $200 listed on Cursor's pricing page; xAI's
  own FAQ lists only the higher tiers) or a linked SuperGrok subscription. Usage is a **weekly
  allowance** with on-demand overage, not per-token billing; allowances do not stack across
  plans.
- Kun Chen's own usage pattern (posts of 2026-08-19 and 2026-08-23): Grok Bot for non-coding,
  always-on, triage-shaped work; feature development stays local "where i have full control".
